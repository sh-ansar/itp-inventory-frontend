# ITP Inventory — P1-A: отраслевые справочники

## Изменения

В разделе «Справочники» добавлены управляемые **в пределах каждой компании** каталоги:
- **Единицы измерения** (неизменяемые системные `pcs/pack/kg/m/l` плюс пользовательские);
- **Производители**;
- **Модели оборудования**, каждая с обязательным производителем;
- **Подразделения**.

Администратор компании и `inventory_manager` могут создавать, переименовывать и архивировать записи. Для всех изменяемых записей есть `version` и защита от устаревшего изменения (HTTP 409). Дубли кода и нормализованного названия исключены на уровне БД в пределах компании/вида/родителя. Просмотр архивных записей доступен отдельно; архив сохраняет историю.

## Интеграция

- **Складская номенклатура:** единицы подгружаются из компании, а допустимая точность (целые или 3 знака) валидируется на Backend при создании SKU и при движениях. Старые единицы не меняются. Нельзя архивировать пользовательскую единицу, пока есть использующая её номенклатура.
- **Имущество:** в форме актива можно выбрать производителя и его модель. На API модель проверяется по производителю, компании и активности; сохранённые исторические архивные назначения не теряются.
- **Ответственные лица:** поле подразделения связано с каталогом той же компании; HRM-синхронизация остаётся отдельным будущим шагом.
- **Мультиязычность и стиль:** RU/EN/GE, общие BaseSelect/BaseDialog/BaseDataTable/BaseButton, встроенные системные единицы имеют локализованные подписи.

## Backend и миграции
- `2026_11_03_000013_create_industry_catalog_items` — справочники, индексы уникальности, composite FK по компании.
- `2026_11_03_000014_link_industry_catalogs_to_assets_people` — `manufacturer_id`, `model_id`, `department_id` и tenant-safe FK.

Маршруты:
`GET /api/v1/companies/{company}/industry-catalogs/{kind}?include_archived=1`
`POST /api/v1/companies/{company}/industry-catalogs/{kind}`
`PUT /api/v1/companies/{company}/industry-catalogs/{kind}/{item}`
`POST /api/v1/companies/{company}/industry-catalogs/{kind}/{item}/archive`

`kind` = `unit/manufacturer/model/department`.

### Безопасный выпуск

1. Сверить Frontend/Backend SHA с проверенными PR и текущим `main`.
2. Свежий PostgreSQL backup с проверкой `pg_restore --list` и SHA256. Перед миграциями выполнить dry-run на копии.
3. Развернуть новый неизменяемый Backend, проверить `composer.lock`, `.env`, shared storage и службы; выполнить две миграции.
4. Развернуть Frontend совместно с новым API, сохранив прежние релизы и алгоритм переключения junction.
5. Проверить создание производителя→модели, назначение к активу, подразделение ответственного, пользовательскую единицу в складе, архивирование, роли, смену компании.
6. Пройти RU/EN/GE × light/dark × mobile/tablet/desktop, подтвердить доступность Inventory/API/HRM/Portal.
7. При отказе откатить обе версии приложения; добавленные столбцы при откате оставить, пока не подтверждено безопасное восстановление данных.

## Объём этапа

P1-A **не включает** конструктор динамических атрибутов активов и настройки компаний/шаблоны документов — это отдельные P1-B и P1-C. Кроме того, интеграция подразделений с HRM пока не включена; существующие связанные данные остаются ручными.

Выпуск в production **не подтверждён**, пока не выполнены финальная проверка веток, миграции на копии и адекватный rollback. Не использовать этот документ как утверждение о промышленной приёмке.
