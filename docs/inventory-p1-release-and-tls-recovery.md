## Проверка сервера

Из внешнего GitHub Actions runner домен `platform.itpmining.kz` разрешается в `85.159.27.17`.

При нормальной TLS-проверке все три маршрута дают `UNABLE_TO_VERIFY_LEAF_SIGNATURE`: клиент не может проверить цепочку сертификатов.

Для **разовой диагностической проверки без аутентификации** были сделаны GET-запросы с отключённой проверкой сертификата только в curl; результаты:

| Маршрут | HTTP |
| --- | --- |
| `/inventory/` | 200 |
| `/inventory-api/api/v1/health` | 200 |
| `/hrm/` | 200 |

**Нельзя использовать `--insecure` в приложении, тестах приемки или обычных клиентских запросах.** Обнаруженный дефект TLS остаётся блокирующим для чистой публичной приемки.

## Как исправить HTTPS без воздействия на другие приложения

1. Восстановить Remote Desktop Commander / защищённый доступ к Windows; определить, какое ПО обслуживает порт 443: Apache, IIS, nginx или обратный прокси.
2. Прочитать текущую привязку сертификата, цепочку и имя хоста. Проверить:
   - сертификат содержит `platform.itpmining.kz` в SAN;
   - срок действия и эмитент корректны;
   - **сервер выдаёт полный набор промежуточных сертификатов** до доверенного корневого.
3. Если TLS завершает Apache 2.4.8+, `SSLCertificateFile` должен указывать на файл с leaf+intermediate в правильном порядке, `SSLCertificateKeyFile` — на действующий приватный ключ. Если TLS завершает другой прокси — исправить его конфигурацию, а не Apache вслепую.
4. Проверить конфигурацию до перезагрузки, переключить только нужную конфигурацию и выполнить контролируемый reload/restart с учётом зависимости Inventory HTTP/FastCGI. Не перезапускать HRM/Portal без необходимости.
5. Повторно проверить **без отключения TLS-проверки**:
   `curl -I https://platform.itpmining.kz/inventory/`,
   `curl https://platform.itpmining.kz/inventory-api/api/v1/health`,
   `curl -I https://platform.itpmining.kz/hrm/`.
6. Проверить логин Inventory и доступность HRM/Portal после исправления.
