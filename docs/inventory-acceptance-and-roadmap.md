# ITP Inventory — приёмка, эксплуатационный контроль и развитие

## Текущий статус
- Production UI: r21, Backend r10.
- 80/80 frontend unit, 10/10 компонентных визуальных тестов поиска, прежний production smoke 51/51.
- Изменение двух оставшихся поисков выпущено через PR #33. Справочники P0 и единый фокус multiselect выпущены через Frontend PR #35 и Backend PR #18. Настраиваемые отраслевые справочники, конструктор полей и шаблоны компании остаются P1.
- **Полная авторизованная визуальная приёмка всех страниц/ролей НЕ подписана.**
- Причина: локальный QA web-session /auth/me работает (200), но auth:sanctum /api/v1/me и /api/v1/companies возвращают 401. Временные диагностические изменения QA откатили.

## Критерии окончательной подписи
- Проверить под company admin, inventory manager и viewer, включая запреты действий.
- RU/EN/GE × light/dark × 390/768/1440 на каждой рабочей странице, дополнительно 320 и 1024 на сложных формах.
- Обязательные маршруты: /registry, /people, /warehouses, /stocktakes, /disposals, /references, /facilities, /reports, /company-roles; динамические /facilities/:nodeId/plan, /stocktakes/:sessionId, /scan/:publicId.
- Скриншоты основных страниц и открытых форм, dropdown, ошибок валидации, пустых состояний, длинных названий, загрузки.
- Отсутствие переполнения viewport, JS pageerrors, HTTP 5xx, неразмеченных полей, ошибок переводов и изменений данных чужой компании.
- Сохранение/отмена/подтверждение изменения, сортировки/фильтров/таблиц, меню, печатных форм и мобильных касаний.
- Запись в протокол: дата, SHA, окружение, компания (обезличенно), роль, маршруты, результат, ссылки на снимки, список дефектов и решение о выпуске.

## Незакрытый дефект QA
1. Проверить сессию после web login: Set-Cookie, cookies same-origin, auth/web и Sanctum API.
2. Сравнить middleware stack изолированного QA с production (без раскрытия секретов).
3. Выполнить API integration regression: login 200, /auth/me 200, /api/v1/me 200, /api/v1/companies 200, logout → 401.
4. Запускать тесты на отдельной обезличенной тестовой базе; не отключать auth/csrf как «обход».
5. Только после устранения причины прогнать Playwright и подписать отдельный протокол полной приёмки.

## План улучшений по приоритетам
### P0 — промышленная безопасность и контроль
- Повторяемые авторизованные E2E тесты с точной проверкой сессии, RBAC и tenant-isolation.
- Независимый мониторинг API 401/403/419/500, журнал операций и контроль резервного восстановления.
- Контроль идемпотентности массовых операций, подтверждения критических действий.

### P1 — эргономика и полнота сценариев
- Сравнение рабочих страниц по эталонным скриншотам HRM (visual diff в CI).
- Единая доступность: focus trap, Esc, keyboard navigation, контраст, hit targets 44 px.
- Быстрые сохранённые представления таблиц и рабочие фильтры по объектам/ответственным.
- Улучшение интерактивного плана: подписи узлов, масштаб, удобное добавление оборудования.

### P2 — развитие продукта
- Интеграция с ERP/1C/учётными системами через staging imports, mapping, dry-run и audit.
- Плановые и внеплановые инвентаризации, согласования, мобильное сканирование.
- Сверка движений имущества, контроль отсутствующих/дублирующихся инвентарных номеров.
- Сводные PDF/Excel отчёты для руководителей и материально-ответственных лиц.
- Производительность на 10k+ активов, observability и изоляция компаний в фоновых задачах.

## Безопасная уборка сервера
1. Сначала инвентаризация: каталоги releases/QA, дата изменения, размер, active junction, зависимости служб.
2. Хранить текущий и минимум предыдущий работающий релиз, manifest/SHA, все значимые backups.
3. Запрещено удалять .env, ключи, секреты, пользовательские вложения, БД, журналы без срока хранения, каталоги HRM/Portal.
4. Кандидаты на очистку: одноразовые Playwright-скриншоты и временные QA-скрипты после архивирования результатов и проверки отсутствия зависимостей.
5. Составить протокол удаления с путём, размером, причиной, возможностью восстановления и хешем архива.
6. Критические архивы не удалять без утверждённой политики хранения.
